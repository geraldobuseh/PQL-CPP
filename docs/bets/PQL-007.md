# PQL-007: Portfolio

## Bet and resolution signal

One portfolio can maintain coherent cash, positions and accepted transaction history
while restricting strategy inputs to detached read-only data. Success means that
accepted trades update all three together, rejected trades leave all three unchanged,
replay reconstructs identical state, and the strategy input type cannot apply trades.

The learning objective is to distinguish read access from mutation authority and to
stage a financial update so a failure cannot change cash without recording its trade.

## Public contract

Include `domain/portfolio.hpp` and link `pql_domain`. The ticket's camelCase operation
names are preserved; existing Position/Trade methods keep their existing spelling.

| Operation | Behavior |
| --- | --- |
| `Portfolio::create(PortfolioId, Money)` | Reject negative starting cash; otherwise start with empty positions/history |
| `applyTrade(const Trade&) -> bool` | Atomically apply an accepted fill; false leaves the portfolio unchanged |
| `cashBalance() -> Money` | Current nonnegative cash |
| `marketValue(const vector<MarketPrice>&)` | Checked sum of open-position values; returns optional Money |
| `totalValue(const vector<MarketPrice>&)` | Checked cash plus market value; returns optional Money |
| `positions()` | Const reference to owned Position values, including liquidated positions |
| `transactionHistory()` | Const reference to accepted Trade records in application order |
| `startingCash()` | Original cash needed to reconstruct state |
| `Portfolio::replay(id, startingCash, history)` | Reconstruct using the same trade validation; reject inconsistent history |
| `snapshot()` | Independent PortfolioSnapshot for strategy reads |

For this scope, every transaction is an accepted full-fill Trade, already carrying
OrderId, symbol, side, quantity, execution price and time. Initial funding is retained
separately as starting state. There is no separate duplicate cash-delta record to
disagree with the fill. The in-memory history is the replay source, not durable
storage; future persistence must store it together with identity and starting cash.

## Non-negotiable strategy boundary

Trusted execution/orchestration owns Portfolio and calls `applyTrade()`. Strategies
receive **PortfolioSnapshot**, never Portfolio, Portfolio pointers/references, or a
trade-application callback. The required future shape is:

```cpp
// Strategy reads a detached snapshot and proposes orders only.
std::optional<pql::Order> propose(const pql::PortfolioSnapshot& input);
```

Snapshot owns copies of cash, positions and history. It has no `applyTrade`, no
conversion to Portfolio, and no reference back to the authority. Its container
accessors are const. Replacing a local snapshot or changing copied holdings cannot
change the real portfolio. A snapshot also survives authority destruction and does
not change when the authority accepts another trade.

Compile-time tests enforce the snapshot's restricted API; a test strategy stub
proposes an Order without any state change, followed by a separate trusted fill
application. No actual strategy framework or caller exists yet. Future integration
must preserve this input signature; passing Portfolio directly would violate the
contract. This is an application architecture boundary, not a sandbox for hostile C++.

## Financial update and replay rules

- Starting cash is finite and nonnegative. There are no margin purchases.
- Buy cash decreases by quantity times fill price; insufficient cash is rejected.
- Sell cash increases by those proceeds only if Position accepts the sale. No short
  position can be created.
- Accepted OrderIds are unique across all symbols in this portfolio. Identical and
  changed-payload duplicates are rejected because the current Trade is a full fill.
- Execution timestamps cannot decrease globally. Equal-time trades retain supplied
  order; replay does not sort or silently repair inconsistent input.
- Flat positions remain to preserve realized history and support reopening.
- Failed validation never consumes an OrderId or appends history.

Position and cash candidates are validated first. All allocating work occurs on a
copy of the state; no-throw swaps commit it only after position replacement and
history append succeed. Allocation failure can still throw, but cannot partially
commit financial state. Snapshot assignment uses the same copy-before-swap principle.
Rvalues deliberately copy snapshot data so their sources retain coherent histories.

## Mark and arithmetic rules

`MarketPrice` contains typed Symbol and Price. A quote is required for every open
position; no quote is needed for a flat position. Missing or duplicate symbols reject
the entire valuation, including identical duplicates or duplicated unused symbols.
Unique extra quotes are harmless. Acquisition prices are never substituted for
missing marks. Totals accumulate in stable first-position-appearance order, regardless
of quote order.

Arithmetic uses the existing approximate double primitives. Reject overflowing or
underflowing positive notionals, lost cash adjustments, lost positive sum terms and
Position-level arithmetic failures. No epsilon permits overspending or overselling.
Mark timing/freshness remains caller-controlled because Price has no timestamp.

## Hand-calculated validation

Start with $10,000. Buy 10 SPY at $100 and 20 AAPL at $50: cash is $8,000, market
value at those same marks is $2,000, and total value is $10,000.

Sell 4 SPY at $120: cash becomes $8,480. With supplied marks SPY $120 and AAPL $45,
remaining market value is `6 * $120 + 20 * $45 = $1,620`, so total value is $10,100.

Sell all 20 AAPL at $45: cash becomes $9,380, SPY is worth $720, and total remains
$10,100. Realized P&L is `$80 - $100 = -$20`; unrealized SPY P&L is $120. Their sum,
$100, equals total value minus initial capital. The sale preserves value at the
unchanged marks; it transfers value from holdings to cash.

## Scope and remaining unknowns

This is one-currency, long-only accounting with no fee fields in current Trade.
Omitted fees do not imply free execution. Slippage/fees, external deposits and
withdrawals, corporate actions, durable persistence, cross-portfolio order attribution,
and the strategy/execution framework remain separate work. Trade has no PortfolioId;
trusted routing must select the correct portfolio. OrderId uniqueness is local to
each portfolio. No live brokerage, return metric or benchmark claim is introduced.

PQL-006 changes remain preserved in the workspace.
