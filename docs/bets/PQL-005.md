# PQL-005: Order and Trade domain models

## Bet

Separate request and fill-record values can express simulated market buys and
sells while preventing invalid quantities and inconsistent order/trade attributes.
The resolution signal is passing deterministic tests for both sides, quantity
rejection, field preservation and execution timestamps, plus compile-time checks
that callers cannot bypass validated construction.

The learning objective is to distinguish a request from its consequences: an Order
asks for a trade; a Trade records a supplied fill. Neither changes portfolio state.

## Contract and implementation

Link the existing `pql_domain` target and include `domain/order.hpp` or
`domain/trade.hpp`. Both models use the PQL-004 primitives, private owned storage,
read-only accessors, value semantics and exact same-type equality.

`Order::create_market(OrderId, const Symbol&, OrderSide, Quantity, Timestamp)` returns
`std::optional<Order>`. It preserves all inputs and supplies `OrderType::Market` and
`OrderStatus::Pending`. `OrderSide` exposes only `Buy` and `Sell`; cast values outside
those enumerators are rejected. Type and status cannot be supplied or changed by
callers. Only the pending creation state is modeled in this ticket.

Order quantities must be strictly positive. The primitive Quantity already rejects
negative and non-finite values, but permits zero for holding magnitudes; the Order
factory adds the stronger rule and rejects both signs of zero. Fractional quantities
are valid for both sides. No raw-double construction overload is provided.

`Trade::create(const Order&, Price, Timestamp)` returns `std::optional<Trade>` for a
full-fill record. It owns copies of the originating OrderId, Symbol, side and entire
positive quantity, together with the supplied execution price and timestamp. Those
request fields cannot be supplied separately and therefore cannot disagree with
the originating order. Price is validated by the existing primitive. Execution time
must be at or after submission; equal timestamps are valid. No wall clock, price
selection, financial arithmetic or implicit timestamp is used.

```cpp
const auto id = pql::OrderId::create(1);
const auto symbol = pql::Symbol::create("SPY");
const auto quantity = pql::Quantity::create(0.5);
const pql::Timestamp submitted{pql::Timestamp::Value{std::chrono::milliseconds{1000}}};
if (id && symbol && quantity) {
    const auto order = pql::Order::create_market(*id, *symbol, pql::OrderSide::Buy,
                                                 *quantity, submitted);
    // Check order before passing it to the future execution layer.
}
```

## Execution boundary and constraints

These are simulation data models, not a broker or execution engine. Constructing a
Trade records a supplied execution; it does not execute or authorize an order,
update its pending status, mutate holdings, or prevent duplicate fills. Lifecycle
transitions and one-time execution belong to a later execution/ledger ticket.

No short-selling behavior is implemented. Buy/Sell and positive quantities alone
cannot enforce a holdings-dependent rule. Before a sell is filled, future execution
must atomically verify requested quantity does not exceed the portfolio's available
holdings. Positive sell quantity is a magnitude, not permission to create a negative
position. Buy-side cash sufficiency likewise needs portfolio context.

There are no limit/stop prices, option contracts, partial fills, live broker calls,
balance calculations, portfolio mutations or strategy behavior. Portfolio/strategy
attribution and fee/slippage capture remain future requirements; omission does not
mean execution is free. No return or benchmark claim is made. Exact decimal
accounting and checked notional arithmetic remain separate from these value models.

## Validation and unknowns

`test/test_order_trade.cpp` exercises both sides, fractional quantities, zero,
negative and non-finite rejection across the primitive/model boundary, invalid enum
casts, field preservation, source ownership and move behavior, explicit timestamps
around the epoch, and rejecting fills before submission. Compile-time checks cover
construction restrictions and typed input boundaries. Existing primitive and smoke
tests remain part of CTest.

Review evidence and executed commands are in `.codex/reviews/PQL-005/`. Execution,
cash/holdings checks, status transitions, duplicate-fill prevention, persistence and
cost accounting have not been implemented or validated by this ticket.
